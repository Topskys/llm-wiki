# 共享状态驱动协作

## 链路示例图

```mermaid
flowchart LR
    RS["研究节点<br/>写入结构化资料"] --> S["共享状态S<br/>进度·预算·产物·检查点"]
    S --> WR["写作节点<br/>读取干净资料"]
    WR --> VT["验证节点<br/>写回评审结果"]
    VT --> S
```

## 核心结论

> **节点不必讲长故事，只更新必要字段。**

- 多智能体协作有两条路：**消息驱动（聊）** 与 **共享状态驱动（态）**，后者是 Graph 架构的正确姿势。
- 共享状态让每个节点只读取和更新**完成当前任务所需的字段**，结构化读写、状态清晰可观测，天然便于暂停、回放和恢复。
- 节点间协作方式**直接决定 Token 成本与可观测性**——消息互发的长上下文是 Token 爆炸的重要来源。

## 要点拆解

### 两种协作方式对比

| | 消息驱动（聊） | 共享状态驱动（态） |
|--|----------------|--------------------|
| 交互方式 | 节点互相发送长消息，重复解释执行过程 | 只读取和更新当前任务所需字段 |
| 上下文 | 长消息、高噪声、上下文重复 | 结构化读写，上下文干净 |
| Token 成本 | 持续增加 | 可控 |
| 可观测性 | 难以回放 | 清晰可观测，便于暂停、回放和恢复 |
| 对应 Graph 要素 | — | **S 状态**（共享介质） |

### 链路示例

**研究节点**（写入结构化资料）→【**共享状态 S：进度·预算·产物·检查点**】→ **写作节点**（读取干净资料）→ **验证节点**（写回评审结果）

- 每个节点进来看到的都是**结构化字段**，不是上一个节点的完整思考过程
- 写入与读取通过同一份状态介质解耦，节点可并行、可替换、可单独重试

### 与其他机制的关系

- 是 [[Graph图编排架构]] 四要素中 **S（状态）** 的协作语义展开
- 与 [[状态持久化四能力]] 是同一枚硬币的两面：**共享**解决节点怎么协作，**持久化**解决状态怎么活下来
- 与 [[多Agent上下文路由]] 互补：路由解决"给每个 Agent 什么信息"，共享状态解决"节点之间怎么传"
- 直接抑制 [[单体Loop结构性瓶颈]] 中的上下文稀释（噪）问题
