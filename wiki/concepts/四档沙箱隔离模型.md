# 四档沙箱隔离模型

## 核心结论

- 沙箱的核心矛盾：Agent 会执行"不是你写也无法 review"的代码——可能来自客户 build 步骤、学生提交、或刚读网页后决定执行的 shell 命令[[10]](#ref-10)。
- 四档沙箱按隔离强度递进：**T1 Wasm → T2 容器 → T3 硬化容器/gVisor → T4 microVM**，信任边界差异是核心。
- 生产级沙箱需**纵深防御**：隔离边界、资源限制、网络控制、权限范围与监控缺一不可[[11]](#ref-11)。

## 四档对比

| 档位 | 隔离技术 | 适用场景 | 权限边界 |
|---|---|---|---|
| T1 Wasm 组件 | 无 ambient authority，按 import 声明授权 | 单 purpose 工具、MCP server | 仅 import 声明的能力 |
| T2 容器 | Docker / Podman，共享内核 | 受信代码、代码库内 Agent | namespace + cgroup，需限制网络 |
| T3 硬化容器 / gVisor | 用户态内核拦截 syscall | 运行 LLM 生成的不完全可信代码 | syscall 级拦截，仍共享内核 |
| T4 microVM | Firecracker / Kata，独立内核 | 开放式 coding agent、任意 shell | 最强隔离，worst case 是"扔掉容器" |

## 要点拆解

- **信任边界差异是关键认知**：容器共享宿主内核、仅适合受信代码；gVisor 用用户态内核拦截 syscall、仍共享内核边界；Firecracker 等 microVM 给每个 workload 独立 guest 内核、隔离最强。
- **绕过审批只有在沙箱边界之后才可接受**：沙箱内不应有生产凭证、共享状态写权限或通往关键系统的网络路径（联动 [[Agent最小权利与审批门]]）。
