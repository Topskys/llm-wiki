# 向量数据库与传统数据库对比

## 横向对比

| 对比项 | 传统数据库 | 向量数据库 |
|--------|-----------|-----------|
| 代表 | MySQL、PostgreSQL、MongoDB | Chroma、Milvus、Qdrant、Pinecone |
| 存储对象 | 结构化数据：数字、字符串、日期、JSON | 向量 Embedding + 元数据 |
| 查询方式 | 精确匹配：where name="xxx"、等值、范围查询 | 近似最近邻搜索 ANN：找向量空间里最相似的 TopK 向量 |
| 索引 | B 树、哈希索引、倒排索引 | HNSW、IVF、FAISS 等向量专用索引 |
| 核心能力 | 事务、关联查询、分页、聚合、强一致性 | 海量向量快速相似度检索，支持向量过滤 |
| 适用场景 | 业务订单、用户信息、日志，关键词搜索 | RAG 知识库、图文检索、推荐、人脸检索 |
| 短板 | 向量检索极慢，向量一多基本不可用 | 不擅长复杂事务、多表 join，不适合精确业务查询 |

## 要点拆解

- **传统库也能存向量字段**：PG 用 pgvector 插件，本质是给关系型数据库增加向量能力，大规模千万/亿级检索性能弱于专业向量库。
- **ANN 与精确匹配的本质区别**：传统数据库是"找完全符合条件的数据"；向量数据库是"找看起来最像的几条"——不是 100% 全局最相似，是牺牲一点召回精度换毫秒级查询。
- **pgvector 开放向量索引后**：底层 ANN 实现相比专业向量库，在亿级向量场景优化弱一些。
