# 豆包：LLM 应用里的权限最小化落地

> 来源：豆包会话共享链接，主题「LLM 应用里的权限最小化（Principle of Least Privilege）落地」。

## 核心思想

> **模型本身不拥有任何权限；模型只负责输出意图/参数；所有真实操作由代码层执行，并且只授予完成当前任务刚好够用的权限，多余权限一律砍掉。**

很多 Agent 出事，根源就是：模型输出的参数直接交给工具执行，工具账号权限过大。权限最小化要拆成 4 层：**模型层权限、工具/函数权限、数据访问权限、运行时环境权限**。

## 1. 模型层：模型没有权限，只有"提案权"

模型不能直接操作资源，只能生成结构化参数（JSON），**无权决定是否执行**。

**错误做法**：
```
用户：帮我删除id=100的订单
模型输出：调用delete_order(100)
代码直接执行！
```
一旦提示词注入，攻击者可以让模型输出 `delete_order(999)` 删别的数据。

**正确做法**：
1. 模型只输出**意图 + 参数**，例如：`{ "action": "delete_order", "order_id": 100, "reason": "用户请求" }`
2. **代码层做决策校验**：不是模型说执行就执行。
3. 系统提示里明确告诉模型：你只能生成参数，不能直接执行操作。

> 一句话：**模型是打字员，不是管理员。**

## 2. 工具（Function Call / MCP）权限最小化（最关键）

每个工具单独隔离，遵循**最小权限 + 参数强校验 + 操作白名单**。

### ① 工具粒度拆分，不要写万能大工具

- ❌ 坏：`db_query(sql)` 万能查询，可以 `DROP TABLE`、查所有用户
- ✅ 好：拆成细粒度工具：
  - `get_user_balance(user_id)`：只能查余额，固定预编译 SQL，**不能传入任意 SQL**
  - `cancel_my_order(order_id)`：只能取消当前登录用户自己的订单
  - `send_message_to_customer_service(content)`：只能发给客服，不能任意手机号/用户 ID

> 原则：**禁止通用动态查询工具（raw sql、raw shell、http 任意 url）**。

### ② 工具参数强制校验（代码层，不要交给 LLM）

校验项：
- 类型校验：数字、字符串长度、格式（手机号、ID）
- 值范围白名单：`order_id` 必须是数字，且属于当前用户
- 权限主体校验：**资源归属校验**（用户 A 不能操作用户 B 的订单）
- 危险字段黑名单：禁止传入 `DROP`、`DELETE`、`../`、`file://`

```python
def cancel_order(operator_uid: str, order_id: int):
    # 1. 校验 order_id 是否为整数
    if not isinstance(order_id, int):
        return error("参数非法")
    # 2. 校验：这个订单是不是 operator_uid 拥有的
    order = db.select("* from orders where id = %s", order_id)
    if order.owner_uid != operator_uid:
        return error("无权操作")
    # 3. 才执行取消
    ...
```

> ⚠️ **校验代码不能写在 prompt 里**，必须在 Python/后端代码硬编码。模型绕过 prompt 很容易，但很难绕过后端代码校验。

### ③ 工具账号/身份隔离

- 查询订单：只读数据库账号（SELECT only，没有 DELETE/ALTER 权限）
- 发送消息：专用消息服务 token，只能发消息，不能读用户全部消息
- 文件读取：单独的只读存储账号，限定目录，不能向上跳 `../`

> 即使 Agent 被注入劫持，拿到的也只是一个只读账号，无法删库。

## 3. 数据访问权限最小化

LLM 不能一次性拿到全量数据，遵循**按需分片**。

**RAG 场景重点**：
1. **检索时带上用户身份过滤**：检索向量库时增加 `uid = 当前用户` 过滤条件，用户只能检索自己的文档。不做这个：注入后模型可以检索别人的隐私文档。
2. **文档分片脱敏**：手机号、身份证、密钥入库前脱敏。
3. **限制返回上下文长度**：不要一次性返回几百条记录。

> 不要把全量知识库一股脑丢给模型，模型看到的数据范围也要做权限边界。

## 4. 运行时环境权限最小化（部署侧）

Agent 后端服务本身也要降权：
- **容器**：非 root 用户运行；只读文件系统；限制 CPU/内存；网络策略禁止出站访问内网其他服务。
- **密钥管理**：不要硬编码密钥，使用密钥管理服务；工具 token 按最小权限申请。
- **日志**：模型输入输出日志禁止记录明文敏感信息。

## 5. 敏感操作：增加审批/二次确认机制

高危操作（删数据、转账、修改配置）**不能模型一键执行**：
1. 模型生成操作请求
2. 返回给前端，展示操作内容，等待用户手动确认
3. 用户确认后，后端才执行工具调用

分级策略：
- 低风险（查询余额、查订单）：自动执行
- 中风险（修改收货地址）：简单校验后执行
- 高风险（删除订单、资金操作）：人工确认

## 6. 审计与边界兜底

权限最小化不是一次性配置，配套：
1. **所有工具调用完整审计日志**：谁、什么 prompt、模型输出参数、校验结果、是否执行。
2. **速率限制**：防止注入后批量调用工具扫数据。
3. **熔断**：短时间大量失败权限校验请求，直接封禁会话。

## 7. 常见踩坑案例

1. ✘ 给 Agent 一个数据库写账号，还提供通用 SQL 工具 → 注入直接删表
2. ✘ RAG 检索不做用户隔离，所有文档都能检索 → 越权读取别人隐私
3. ✘ 工具参数只靠 prompt 校验，后端不校验资源归属 → 越权修改他人数据
4. ✘ 一个万能 http 工具，可以访问任意内网地址 → SSRF，渗透内网

## ✅ 最简落地清单

1. 模型只生成结构化参数，**无权执行任何操作**
2. 拆分细粒度专用工具，**禁用 raw sql / shell / 任意 http**
3. 所有工具调用在代码层做：类型校验 + 资源归属校验 + 参数白名单
4. 工具使用最小权限账号（只读优先）
5. RAG 检索带上用户身份过滤
6. 高危操作增加人工确认
7. 容器降权、密钥隔离、审计日志
