# DeepSeek：AI Agent 防提示词注入方法

> 来源：DeepSeek 会话共享链接，主题「防提示词注入方法 / agent 防提示词注入方法」。答卷先给出普通 LLM 应用的纵深防御框架，再重点给出针对 Agent 场景的架构级防御路线（引用 30+/79 个网页，覆盖 CaMeL、DRIFT、Task Shield、MELON、NOVA、Janus、IPIGuard 等）。

## Part 1：普通 LLM 应用的纵深防御四层

防范提示词注入没有"银弹"，核心挑战是 LLM 在架构上无法从根本上区分"指令"和"数据"。有效防御必须是一个**分层、纵深**的系统，即使单点被突破也将损害控制在有限范围。

### 第一层：输入侧治理与检测（安全前置）

- **输入安全检测**：请求链路入口部署检测层。风险分类需重点检测：**系统指令窃取**（输出你的系统提示词）、**规则覆盖**（忽略以上所有指令）、**间接注入**（文档/网页夹带指令）、**多轮诱导**。技术手段：基于 Transformer 的模型理解上下文识别隐含恶意意图（非仅关键词匹配）；对 Unicode 隐形字符、编码混淆等绕过技术规范化处理。
- **指令与数据分离**：结构上将用户输入、检索文档等不受信内容与系统指令分开。方法：使用带**每次请求唯一随机数（Nonce）**的分隔符包裹不受信内容，如 `<<<DOCUMENT nonce=abc123>>> ... <<<END nonce=abc123>>>`，攻击者无法伪造边界注入指令。
- **检索内容清洗**：对 RAG 从外部知识库/网页/邮件检索的内容清洗，删除隐藏 HTML 标记、脚本或可疑指令。

### 第二层：模型与架构层加固

- **能力沙箱（Capability-based Sandbox）**：采用类似 CaMeL 的架构，将 LLM 置于基于能力的执行层中。**双 LLM 架构**：一个"特权 LLM"处理用户指令并制定计划，另一个"隔离 LLM"处理不受信内容，强制执行严格模式验证，不受信数据无法直接触发工具调用。
- **最小权限工具限定**：每个 Agent 配置**工具允许列表**，严格限定只能调用完成当前任务必需的工具，限制注入成功后的影响范围。
- **结构化提示与动态分隔符**：用结构化格式（JSON）组织提示词，动态生成每次请求不同的分隔符/随机数，让模型更容易区分指令和数据。

### 第三层：输出侧验证与人工审核

- **输出验证与审计**：模型输出应用前检查：是否泄露敏感信息（系统提示词、内部数据），是否尝试调用未授权工具。
- **高风险操作人工审批**：对**真实副作用**操作（发邮件、支付、修改生产环境数据）必须设**人工审批关卡**。这是最终决定性屏障，模型无法"说服"确定性检查的人类审批者。

### 第四层：持续监控与运营

- **全链路日志与审计**：记录完整请求链路（输入、检索内容、工具调用、输出），事件发生后可追溯分析。
- **对抗性测试**：CI/CD 集成对抗性测试框架，用含提示注入、数据外泄攻击样本的测试集持续评估防御有效性。
- **账号风控**：识别批量攻击、异常调用模式——攻击往往不是单次请求而是自动化脚本组合。

> 总结：关键在于**放弃对单一"完美过滤器"的幻想**，构建假设"攻击最终会成功"的弹性系统：入口识别净化 → 架构权限隔离与数据/指令分离 → 出口验证与强制人工干预 → 全程监控测试迭代。

## Part 2：Agent 专属防御（核心）

针对 AI Agent 的防御逻辑与普通 LLM 应用有本质区别：Agent 具备**自主规划**和**工具调用**能力，一旦注入，攻击者不仅能窃取信息，还能通过工具调用产生**真实世界副作用**（发邮件、执行代码、修改数据）。因此 Agent 防御核心是：**在架构层面假设注入终将发生，通过隔离、权限最小化和执行管控，让被劫持的 Agent 也无法造成实质性破坏**。

### 🧱 架构层：控制流与数据流隔离（最核心防线）

本质借鉴传统软件安全的**控制流完整性**原则。

**1. CaMeL：基于能力的沙箱架构**（Google DeepMind）

- **核心机制**：特权 LLM（处理可信用户指令）生成用**受限 Python 子集**编写的"程序"，编排所有步骤。程序从不可信来源（被隔离的 LLM 或工具）接收数据时，为每个数据值附加**能力元数据**，跟踪来源和允许操作；任何数据操作必须通过能力检查。
- **效果**：在 AgentDojo 安全基准测试中，CaMeL 抵御 **67%** 的攻击。
- **延伸**：针对 Computer Use Agent（CUA），变体 **NOVA** 采用**单次规划**（single-shot planning）——可信规划器开始在即生成覆盖所有预期运行时状态的完整分支计划，根治任意指令注入对控制流的劫持。

**2. 双 LLM 模式：物理隔离可信与不可信**（Simon Willison 提出，CaMeL 借鉴扩展）

核心原则：**永远不要让不可信文本接触到拥有秘密或权限的模型**。

- **特权 LLM**：只处理用户原始指令，负责管理工作流，不直接接触任何外部不可信内容。
- **隔离 LLM**：专门接触不可信数据（网页、邮件、文档），但**无法调用任何工具**，只能从中提取特定信息（如邮箱地址）返回给特权 LLM。
- 攻击即使成功注入隔离 LLM，也无法触发任何有副作用的操作。

**3. 分层内存隔离**

- **DRIFT 框架**引入 **Injection Isolator**，专门检测并屏蔽记忆流中与用户原始查询冲突的指令，防止注入在长期交互中持续发酵。
- **AgentSys** 采用操作系统式**分层内存管理**：主 Agent 派生的 worker Agent 在隔离上下文执行，外部数据和子任务推理轨迹**永远不会直接进入主 Agent 内存**，只有经过 schema 验证的返回值才能跨越隔离边界。

### 🎯 规划与执行层：任务对齐验证

Agent 规划过程是注入攻击的主要目标。防御关键：**持续验证每一步行动是否仍服务于用户原始意图**。

**1. Task Shield：任务对齐验证**（ACL）

- 将安全视角从"阻止有害行为"重新定义为**确保任务对齐**。测试时系统性地验证每条指令和每次工具调用是否对用户指定目标有贡献。
- AgentDojo 基准：攻击成功率降至 **2.07%**，同时保持 **69.79%** 任务效用。

**2. DRIFT：动态规则与计划偏差检测**（NeurIPS）

三步工作流：
- **Secure Planner**：根据用户查询构造最小化功能执行轨迹和 JSON Schema 风格参数检查清单。
- **Dynamic Validator**：监控执行是否偏离原始计划，评估变更是否符合权限限制和用户意图。
- **Injection Isolator**：从记忆流中检测并屏蔽与用户查询冲突的指令。

**3. MELON：掩码重执行与工具比对**（ICML）

关键观察：**成功攻击下，Agent 下一步行动会变得对用户任务依赖更少、对恶意任务依赖更多**。做法：用掩码函数修改用户提示后**重新执行 Agent 轨迹**，若原始执行与掩码执行的行动高度相似则判定遭受攻击。实验显示阻止**超过 99%** 攻击，同时保持良好任务效用。

### 🔧 工具调用层：零信任执行管控

Agent 特有且最关键的防御层面。即使 Agent 被注入并试图调用工具，**工具调用网关**也能在副作用发生前拦截。

**1. 细粒度策略执行（Janus）**：在**每一个工具调用**执行前拦截，依据**参数级 JSON Schema 条件**验证，严格最小权限。策略可从 JSON 文件加载或由 LLM 根据查询自动生成，执行中**增量收紧**。支持**污点跟踪**：记录会话读取过哪些不可信来源，对出站或改变状态的工具调用进行门控。

**2. 能力沙箱与权限声明（Agent Runtime）**：每个工具必须**声明所需权限**，运行时仅在全部要求满足当前授权集时才允许调用。直接阻止注入在无显式操作员批准时**升级为文件写入、网络调用或 shell 执行**。

**3. 工具依赖图（IPIGuard）**：将任务执行过程建模为在**计划好的工具依赖图**上的遍历，偏离既定路径的工具调用视为可疑并阻止。

**4. 计划-执行分离架构**："先计划，后执行"天然抗注入——**控制流在计划阶段已确定**，执行阶段只按计划调用工具，不可信数据无法改变执行路径。

### 📥 输入与输出侧：纵深防御的辅助层

- **输入侧**：对进入 Agent 的外部内容做**隐藏指令检测**，召回时对片段**风险标注**，识别 Unicode 隐形字符、编码混淆等绕过技术。
- **输出侧**：对模型生成的 structured output 做 **JSON Schema 验证**——注入可能通过畸形 JSON、额外字段或类型混淆进入下游执行链；同时检测敏感信息泄露迹象。

### 📊 监控与运营

- **全链路审计**：安全相关事件（工具调用、信任边界穿越、策略违反）生成可追踪遥测数据。
- **Fail Closed 原则**：检测到潜在注入或未授权工具使用时，**拒绝并升级**，而不是继续执行期望无事发生。
- **对抗性测试**：CI/CD 持续运行含注入样本的测试集。

> 总结：Agent 防注入核心范式转变——**从"防止模型被说服"转向"确保模型即使被说服也做不了坏事"**。架构隔离（CaMeL/双 LLM）解决控制流完整性，任务对齐验证（Task Shield/DRIFT）确保行为不偏离用户意图，工具调用策略执行（Janus/能力沙箱）在最后一道关口拦截副作用。三层叠加，企业级部署可将风险控制在可接受范围。
